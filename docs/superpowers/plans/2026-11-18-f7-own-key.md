# F7: Each Doctor's Own Gemini Key, Open to Everyone: Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Anyone with a Google account can sign in to PubMed Ai and run questions on **their own** free Gemini key. The owner pays nothing per run, and the server never stores anyone's key.

**Owner decisions (18 Nov 2026):** 1A: the key lives only in the doctor's browser (an encrypted cookie). The server uses it during a run and never writes it to the database, a log or a file. 2A: anyone with a Google account may sign in; the approved list goes.

**Checked against:** `main` at `18f6b86` (15 Nov, sign-in pages). Facts below come from that commit unless marked *Not checked*.

## How it works today (Fact)

- One key for the whole app: `GEMINI_API_KEY` in `.env` → one `GeminiClient`, one `GeminiPacer`, one `ModelCaller` (`main.py` `open_gemini`).
- One active run for the whole app: `runs_one_active` unique index (`0004_runs.sql`).
- The day count is by model only: `calls_today(pool, model)` (`gemini/quota.py`).
- Sign-in: the gate allows only `gate/emails.txt` (`--authenticated-emails-file`), and the app needs a `users` row (`identity.current_user` raises `NotSetUp`). Roles are `owner`, `surgeon` and `fellow` only.
- Library, Activity and run pages already show only the signed-in user's own runs (`user_id` filters in `runs.py`).

## What changes

| Today | After F7 |
|---|---|
| Owner's key on the server | Each doctor pastes their own key once on a **Your Gemini key** page |
| One run at a time for the whole app | One run at a time **per doctor**, and at most `MAX_ACTIVE_RUNS` (default 2) for the whole app |
| One pacer and one day count | One pacer and one day count **per doctor** |
| Approved list | Anyone with a Google account; a `users` row is made at first sign-in |
| "Free runs left today: about N" (the app's) | The same line, counted on **your** key |

With no key saved, the key-word search still works, and the question box links to the key page. The app already handles a missing key this way.

## Global Constraints

1. **The key is never stored.** It is not in any table, log line, URL, redirect, page HTML, error message or exception text. It exists only in the encrypted cookie and, during a request or a run, in memory (a `SecretStr`). Tests prove this for every route (extend `tests/test_logging.py`'s leak list).
2. **The cookie:** name `pmai_gk`; value = AES-256-GCM of the key, with the user's email as associated data (so a cookie made under one Google account is ignored under another on a shared hospital computer); `HttpOnly; Secure; SameSite=Strict; Path=/; Max-Age=34560000` (400 days, the most browsers allow), **renewed on every signed-in page load**, so the key stays until the doctor removes it (O3: owner, 18 Nov). Clearing the browser's data also removes it. The secret is the new required `KEY_COOKIE_SECRET` (32 random bytes, base64) in `.env`. A cookie that fails to decrypt is treated as no key and cleared.
3. **The gate and the app stay as they are otherwise:** oauth2-proxy v7.15.6, no skip-auth rule, the cross-site guard on every POST (the key form gets it too).
4. **Public-repo rule:** no domains, emails or server names in committed files (existing privacy tests).
5. **No engine change.** Prompts, steps, call caps (`RUN_CALLS = 23`, `RUN_ATTEMPTS = 26`), the model and the answer page stay exactly as they are.
6. **New dependency:** `cryptography` (AES-GCM; Python's standard library has none). Pinned with hashes in `requirements.lock`.

### Task 2: Settings and start-up

**Files:** `config.py`, `main.py`, `compose.yaml`, `.env.example`, `tests/test_config.py`, `tests/test_compose.py`.

- [ ] TDD steps as Task 1. The compose tests change deliberately, not loosened.

### Task 3: Migration `0008_own_keys.sql`

- `users.role` CHECK gains `'user'` (made at first sign-in). The owner stays `owner`.
- `model_calls.user_id BIGINT REFERENCES users(id)`, nullable (older rows have none), plus index `(user_id, model, quota_day)`. Step CHECK gains `'key_check'`.
- Drop `runs_one_active`; add `runs_one_active_per_user ON runs (user_id) WHERE status IN ('queued','running')`.
- The app-wide cap (`MAX_ACTIVE_RUNS`) is checked in `create_run` inside the same transaction, under `pg_advisory_xact_lock`, so two clicks at once cannot both pass.
- [ ] Tests in `tests/test_migrate.py` and `tests/test_runs.py`: a second run for the same user → `ActiveRunExists(own=True)`; two users can run at once; a third when the cap is 2 → new `AppBusy`; no key column anywhere (`information_schema` check: no column whose name contains `key` except existing ones).

### Task 4: Runs use the doctor's key

**Files:** `web.py` (`_start_question`, `run_again`), `runner.py` (`ThreadStarter.start(run_id, key)`, `run_one(..., caller)`), `gemini/quota.py`, `gemini/caller.py`.

- `_start_question`: no key → the home page with "Add your free Gemini key to ask questions" and a link to `/key`, status 403. The order of checks is otherwise unchanged: empty, too long, the day's room **for this user**, the patient-details check, the active-run checks, start.
- The run thread gets a `ModelCaller` built for that run: a `GeminiClient` holding the doctor's key, and that doctor's pacer. When the thread ends, the client is closed and the key is released.
- **Pacers per doctor:** a small `PacerBook` keyed by user id; an entry is dropped after 10 minutes unused.
- `calls_today(pool, model, user_id)`, `runs_left(..., user_id)`: count by user. Every `model_calls` insert carries `user_id`.
- A restart in the middle of a run: the run fails as `stale`, as today. The key is gone with the process; the doctor presses Run again.
- A key Google refuses during a run (400/403), or a billing-linked project (402): the run fails with the kind already used (`key_refused` / `billing_refused`). The run page adds one line: "Google refused your key. Check it on the Your Gemini key page."
- [ ] Tests (with `gemini_fakes.py`): two users' runs use two different keys (the fake sees each key only on its own user's requests); user A's 429 `daily_limit` does not change user B's count; the key does not appear in `caplog`, the database (dump every text column) or any response body; `run_again` without the cookie → the "add your key" message.

### Task 5: The "Your Gemini key" page (`/key`)

**Files:** `templates/key.html`, `web.py`, `templates/base.html` (one nav link), `templates/home.html` (a line under the question box).

Plain words, in the SurgeryAi look:
1. **How to get a free key** (four lines): open Google AI Studio's API key page; sign in with any Google account; **create the key in a project with billing turned off** (a billing-linked project is refused, HTTP 402, seen on 10 Nov); copy it.
2. **Paste box** (a password field) and a **Save** button. On Save, the app makes one tiny check call (`key_check`, about 5 output tokens, counted on the doctor's key). Results:
   - ok → "Key saved in this browser."
   - 400/403 → "Google did not accept this key."
   - 402 → "This key's project has billing on. Make a key in a project with billing off."
   - 429 → "This key has used today's free limit. It was saved, and it will work after <reset time IST>."
   - Network error → not saved: "Could not reach Google. Try again."
3. **What happens to your key:** "Only in this browser, encrypted, and only for your Google sign-in. It stays until you remove it. Our server uses it while your question runs and never saves it." Then: "On a new phone or another browser, paste it once more. Clearing this browser's data also removes it." (wording as mock v1)
4. **Google's free tier, in plain words:** "On Google's free tier, Google may use what is sent to improve its products, and people may review it. Do not type patient details (the app also checks for them)." Plus a link to Google's Gemini API terms. *Not checked:* the current age and country limits of the free tier; the page links to Google's terms instead of stating them.
5. **Remove key from this browser** button (clears the cookie).

- [ ] Tests: GET shows "No key saved" or "A key is saved (ends ••••abcd)"; the last four characters are the only part ever shown; POST with the cross-site guard; each of the five results above with the fake; the page HTML never contains the key; Remove clears the cookie.
