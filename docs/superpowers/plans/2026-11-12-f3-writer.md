# F3: the writer in four parts and the answer page Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Status (12 Nov 2026):** plan only, written by the Architect. Nothing below is built. Every item in "Needs the owner" must be answered before Task 1 starts; the plan is written for the suggested option of each and names what changes for the others.

**Goal:** After the F2 researcher has chosen its studies, Gemini Flash-Lite writes Incisive Quick's answer in four parts at once (summary, context, trials, outcomes) from the selected studies' records and abstracts, with Incisive's prompts and schemas. Code merges the parts into one answer, stores it in Postgres, and draws the answer page exactly as the owner's frozen mock (`docs/mocks/f3-answer-page-v5.html`, version 5, 12 Nov 2026: version 4 with one wrap rule, `body{overflow-wrap:anywhere}`; versions 3 and 4 kept as history): the bottom-line card; "Why this conclusion" with "Every estimate with a 95% CI" beside "Outcome by outcome"; "Counselling dashboard" with "Out of 100 people like those in the trials" beside "Compare the arms"; the trials; the references. Every line, bar, square and fold is computed by code from the stored numbers; the model draws nothing. No JavaScript. ₹0 a run.

**Architecture:** A port of Incisive's Quick writer (`agent/writer_v3.rs`, the "Quick in four parts" section) on the F2 Gemini layer: the same system prompt, user message, schema, four section schemas and instructions, token caps, one retry per part and the one-piece fallback. The four calls run on four threads; the F2 pacer spaces their starts 6 s apart (10 a minute). The merged reply is read and normalised as Incisive's `WireAnswer::into_answer`, then the code-only steps Incisive runs right after the writer and before its checks: evidence labels from the cited designs (`evidence_types`) and the merge consistency notes (`merge_checks`). The answer is stored as one JSON document in a new `answers` table, in the shape of Incisive's `AnswerV3` (Quick fields only). A new page `GET /runs/{id}/answer` renders it from pure derivation functions (`answer_page.py`), ported from Incisive's `answer_page.rs` where Incisive has a rule and defined here, with tests, where the frozen mock needs one Incisive does not have. The citation check, number check and number completion are F4.

**Tech Stack:** As F2. No new dependency. Jinja2 with autoescape, no `|safe`. `concurrent.futures.ThreadPoolExecutor` (standard library) for the four parts.

**Spec:** `.10x/specs/2026-11-10-pubmedgemini-quick-design.md` (§2 decision 3, §3, §5 step 3 and the rules under it, §6 as rewritten on this branch, §7 `answers`, §8, §9 F3, §14). Reference code (read-only): Incisive `crates/incisive-app/src/agent/{team,writer_v3,answer_v3,numbers_complete}.rs`, `answer_page.rs`, `app/page.rs`, `run_tracker.rs`, `runs/mod.rs`. Below, "Incisive `x.rs` `SYMBOL`" means that file and symbol under `crates/incisive-app/src/`, read by the Architect on 12 Nov 2026 at Incisive commit `12630f7` (Fact: `git log -1` in the read-only checkout).

**Owner rules that shape this plan** (coordinator, 11 and 12 Nov 2026):
1. "Follow the same as Incisive quick run": prompts and schemas word for word unless a difference below is approved. Model `gemini-3.5-flash-lite` for every call, REST via `GeminiClient` with `responseSchema`.
2. This small free model will not equal Incisive; do not push it beyond what it can do. Keep instructions simple and concrete; the app's code does the checking and drawing.
3. Never log the question, model text, queries or the key. Answer text lives only in the database.
4. The free-tier budget is the owner's decision (options in "Needs the owner" D1).
5. What the page may draw before F4 is the owner's decision (D3).
6. Every engine change is discussed first; every difference from Incisive is listed below with options and one suggestion.

## Global Constraints

- Everything in F0's, F1's and F2's Global Constraints still holds (one allowed Gemini host, the key only in a header, no automated test reaches the network, CI fails on a skipped test, one run at a time, the patient-details check before anything is sent).
- **Never logged, at any level:** the question, abstracts, titles, the writer's prompt, any part's reply, any field of the answer, outcome names, arm names, Google's error `message`, the key. Writer log lines hold the run id, the part name (`trials`, `outcomes`, `context`, `summary`, `one_piece`), the attempt word (`first`, `retry`), counts, token counts, latencies and fixed kinds only (Incisive `writer_v3.rs` module doc "Privacy"; `log_cut_off` "Sizes and codes only, never text").
- **Answer text lives only in `answers.body`** (and the question in `runs.question`). `model_calls` stays text-free. No answer text in a URL, a log line, an exception message or a step line (step lines hold counts and fixed words only).
- **Untrusted model output:** every part is read strictly and typed (Incisive `read_structured` plus serde's typing of the wire structs); nothing is rendered as HTML (Jinja autoescape; no `|safe`, no `Markup` built from model text); every number drawn passes the code checks of D3 first; style attributes hold only numbers code computed (`left:34.4%`), never model text.
- **The model draws nothing.** Positions, widths, scales, dot counts, pill colours, folds and reference numbers are computed by `answer_page.py` from stored numbers. No JavaScript on any page (`<script` and `on…=` attributes absent: test).
- **References are code's:** built from the fetched records in the researcher's selection order (Incisive `team.rs` `run`, "References are code's"). The model never writes an author, a year or a reference number.
- **Flag, never delete** (spec §5): F3 removes nothing the writer wrote. Where a number fails a drawing check it is shown as text with the reason, not drawn and not hidden.
- Work on branch `f3-writer`. Merging to `main` deploys. Do not merge without the owner's explicit "merge it".

## Review Focus

1. **Part replies that are malformed or hostile:** invalid JSON, a reply cut off at `MAX_TOKENS`, a string where `value` must be a number, `certainty: "medium"`, `ci_low: "0.28 to 0.51"`, `n: "about 300"`, a 40,000-character `effect_text` holding `<script>` and `</details>`, an outcome name holding `"><img`, a `[99999999]` citation of a study not selected, a PMID in `numbers.pmid` not in the references. Tests: Task 4 `test_wire_typing_follows_serde`, `test_unknown_certainty_becomes_very_low_and_is_counted`, `test_ci_bound_as_text_is_kept_in_the_label`; Task 5 `test_a_part_cut_off_gets_one_retry_with_the_nudge`; Task 8 `test_model_text_is_escaped_everywhere_on_the_answer_page`, `test_unknown_citation_is_flagged_not_dropped`.
2. **Numbers that must not be drawn:** RR 0, RR −0.4, lo > hi, an estimate outside its interval, NaN or infinity, a percentage of 140 or −3, an interval 0.0001 to 9,000, a difference whose interval is 0 to 0. Tests: Task 7 `test_draw_checks_refuse_and_say_why`, `test_absurd_interval_is_clamped_to_the_scale_and_says_so`, `test_out_of_100_needs_percentages_in_range`.
3. **The derivation against the frozen mock:** the mock's own numbers must give the mock's positions to one decimal (log scale 0.1 to 2 with 1 at 76.9%; difference scale −8 to +2 with 0 at 80%), its dot counts (9 and 19; 2 and 4), its fold ("Show 2 more outcomes" in the outcomes card, no fold in the counselling pair). Tests: Task 7 `test_forest_positions_match_the_frozen_mock`, `test_fold_matches_the_frozen_mock`, `test_out_of_100_counts_match_the_frozen_mock`.
4. **Rounding:** Incisive's `f64::round` is half away from zero; Python's `round` is half to even (`round(2.5) == 2`). The port must give 3 for 2.5 and 0 for 0.37 (Fact: Incisive `answer_page.rs` `out_of_100_count`, test `out_of_100_count(43.6) == 44`). Test: Task 7 `test_out_of_100_rounds_half_up_as_incisive`.
5. **Four calls on four threads:** the pacer, the day count, the per-run cap and the hard stop are shared; a part that fails never cancels the others (Incisive `write_quick_parallel_with`: "a failed part never cancels the others"); the decision (merge, fall back, fail) is made once all four are in. Tests: Task 5 `test_four_parts_start_six_seconds_apart`, `test_one_failed_part_waits_for_the_others_then_falls_back`, `test_run_cap_reached_mid_writer_fails_the_run`.
6. **Text that must never reach a log line:** Task 9 `test_nothing_of_the_writer_is_logged_in_a_full_run`.

## Calls, the free day and time

Facts used: `RUN_CALLS = 11`, `CALL_RESERVE = 3`, `RUN_ATTEMPTS = 14` (`gemini/quota.py`); `runs_left_for(rpd, used)` = `1 + (rpd − used − RUN_ATTEMPTS) // RUN_CALLS` when `used + RUN_ATTEMPTS ≤ rpd` (`gemini/quota.py` `runs_left_for`); the per-run cap counts every attempt (`gemini/caller.py` `ModelCaller._take_attempt`); 10 requests and 250,000 tokens a minute, 500 a day (`config.py` defaults).

**Calls a run can make (no transport retries), by option** (Fact: arithmetic on the Incisive rules above; F4's number completion is one call, no retry: Incisive `numbers_complete.rs` "No retry"):

| Option | Writer calls at most | `RUN_CALLS` | Cap (`+3`) | Free runs shown on a fresh day (500) | After F4 (+1) |
|---|---|---|---|---|---|
| A. Incisive exactly: 4 parts, one retry each, one-piece fallback with its retry | 4 + 4 + 2 = 10 | 21 | 24 | 23 | 22 (cap 25) |
| B. 4 parts with their retries, no one-piece fallback | 8 | 19 | 22 | 26 | 24 |
| C. 4 parts, no retry, one-piece fallback without retry | 5 | 16 | 19 | 31 | 29 |
| D. One piece with its retry (Incisive's default switch) | 2 | 13 | 16 | 38 | 35 |

**A typical run** (Estimate, from the F2 live test: 8 turns and a valid list first time): 9 researcher calls + 4 parts = 13 calls under A, B or C; 10 under D. Because "Free runs left" counts every later run at its worst case, the page shows 23 on a fresh day under A while about 37 typical runs would fit (a run is admitted while today's count + 24 ≤ 500: 13 × 36 + 24 = 492). The shown number falls by about 0.6 per typical run. Under A the cap leaves 24 − 13 = 11 spare attempts for 429 and 503 retries in a typical run (Estimate).

**10 requests a minute** (Fact: `GeminiPacer` spaces starts 60 / rpm = 6 s apart, one lock for all threads): the four parts start at t, t + 6, t + 12, t + 18 s after the list call's own slot. A part's retry waits for the next free slot. So "parallel" costs 18 s of spacing, not four latencies.

**250,000 tokens a minute** (Estimate, 3 bytes a token as Incisive's estimate and our pacer use): each part receives the whole prompt. Worst case per part: 10 studies at every byte cap (about 66,000 bytes), 10 contradiction notes and 20 searches (about 13,000), the system prompt and its section instruction (about 5,500), the part schema (under 2,000): about 86,000 bytes, about 29,000 tokens. Four parts: about 115,000; with the study-list call in the same minute (F2's worst case about 45,000): about 160,000, under 250,000, so the token pacer does not wait. A typical part (abstracts of about 1,800 bytes) is about 9,000 tokens, 36,000 for the four (Estimate). Gemini's input limit (about 1M tokens) is never close.

**Time** (Fact for the limits: `researcher/loop.py` `TIME_LIMIT_SECONDS = 360`, `WRITER_ALLOWANCE_SECONDS = 150`, `HARD_STOP_EXTRA_SECONDS = 60`, `WRITER_MIN_SECONDS = 150`): research wraps up at 210 s; the hard stop is at 420 s for the whole run, writer included; the writer starts only if at least 150 s are left before the hard stop (that is, by 270 s). Each writer attempt may start until the hard stop and is cut at it (the F2 list call's rule: `deadline = attempt_deadline = hard_stop_at`). A run that passes the hard stop in the writer ends `failed` `hard_stop`, as Incisive. Estimate for the writer: 18 s of spacing plus the slowest part's latency (the outcomes part, up to 12,000 output tokens; Flash-Lite's speed at that length was not measured: Not checked), so roughly 30 to 90 s; with F2's measured research of 1 to 3 minutes a run should end well inside 420 s. A retried part adds one more latency; the one-piece fallback is not tried with less than 150 s left (Incisive).

*Draw checks (D3 option a):* `draw_problem(n: Number, kind: Literal["ratio", "diff", "percent"], refs) -> str | None`, the first that applies, in this order:
- `its study is not in the references` (`n.pmid.strip()` not in `refs`);
- `a value is not a finite number` (value, and for ratio and diff `ci_low`, `ci_high`);
- `a ratio must be above 0` (ratio: value, `ci_low`, `ci_high` all > 0);
- `the interval is reversed` (`ci_low > ci_high`);
- `the estimate is outside its interval` (not `ci_low ≤ value ≤ ci_high`);
- `a percentage must be from 0 to 100` (percent: every arm's value).
A forest row with a problem is listed in the forest as text (label, the numbers as written, `Not drawn: <problem>.`) with no line and no bar. An out-of-100 group with a problem is not an out-of-100 item (it stays in "Compare the arms" as text). Compare rows are text only; an unknown study there reads `PMID <id> (not in the study list)`.

*Forest rows:* `forest(w, refs) -> Forest` with `ratios: list[ForestRow]`, `diffs: list[ForestRow]`, `ratio_axis: Axis | None`. Rows: Incisive `forest_rows` (every number with both CI bounds that is a ratio or a difference), ratios first, then differences, each in outcome order then number order. `ForestRow(label, estimate_text, sub, drawn: bool, problem: str | None, left: float, width: float, est: float, null: float, scale: Axis, aria: str)`:
- `label` = the number's label, else the outcome's name; `estimate_text` = `ratio_estimate` / `diff_estimate`; `sub` = `" · ".join` of the non-empty study name (`study_short` of the trials-table label, else `PMID <id>`, then ` [n]`), the arm, and for differences the unit.
- **Ratio axis** (shared by all drawn ratio rows, folded ones included): `LADDER = (0.05, 0.1, 0.2, 0.5, 1, 2, 5, 10, 20, 50)`. `lo_axis` = the largest ladder value ≤ min(every drawn `ci_low`, 1) and < 1; `hi_axis` = the smallest ladder value ≥ max(every drawn `ci_high`, 1) and > 1; bounds past 0.05 or 50 take 0.05 or 50. Position `log_pos(x) = clamp(100 · log10(x / lo_axis) / log10(hi_axis / lo_axis), 0, 100)`; the dashed mark at `log_pos(1)`. Scale labels: `fmt_axis(lo_axis)` at the left, `1` at the mark, `fmt_axis(hi_axis)` at the right.
- **Difference axis** (one per row): `a = min(ci_low, 0)`, `b = max(ci_high, 0)`; `step` = the smallest of 1, 2, 5 × 10^k (k any integer) with `(b − a) / step ≤ 5` (`step = 1` when `a == b == 0`); `lo_axis = floor(round(a / step, 9)) · step`, `hi_axis = ceil(round(b / step, 9)) · step` (the rounding stops float noise such as −0.3 / 0.1 = −2.9999999999999996 moving an edge), each rounded to 9 decimals; if `lo_axis == 0` then `lo_axis −= step`; if `hi_axis == 0` then `hi_axis += step` (0 is never at an edge). Position linear, clamped 0 to 100. Labels: true minus for negatives, `+` for positives, `0` for zero.
- `left = pos(ci_low)`, `width = max(pos(ci_high) − left, 0.5)` (Incisive's 0.5 minimum), `est = pos(value)`. Percentages are written with one decimal and a trailing `.0` dropped (`34.4`, `20`, `80`).

## Risks carried into F3

1. **The outcomes part is the large one** (spec §11 item 3): up to 12,000 output tokens of nested JSON. A cut-off or unreadable reply costs a retry and maybe the one-piece call. Measured only on the first real runs (Not checked).
2. **The schema on Gemini:** the writer's schema (about 60 properties, nesting four deep, nullable numbers) was never sent to Gemini; a 400 `request_refused` for schema size would fail every writer call. Mitigation: the first real run is the check; if refused, simplifying the schema is an engine change for the owner (Not checked).
3. **Structured numbers on a small model:** Incisive's chart rules depend on the model writing `unit` as `RR`/`OR`/`HR` or `%` and naming arms. If Flash-Lite puts "RR" in the label instead, the forest is empty and the numbers stay text (correct but plain). The page code is right either way; the quality question is F5's (Estimate).
4. **Pace and time:** 18 s of spacing plus the outcomes part's latency, after up to 3 minutes of research; a 429 wait or a retry can push a run to the 150 s writer gate (partial with references) or the hard stop (failed) (Estimate).
5. **The weights of the fold** are estimates from the mock's CSS; on a real page the pair may still differ by one item's height. The rule is fixed and tested; tuning the weights later changes only constants.
6. **Python and Rust differences** in the ports: rounding (covered), float printing (`fmt_value` for large non-whole numbers: Python writes `1e+16`, Rust writes all digits; not expected in clinical numbers), regex Unicode classes (the F2 `deid` lesson; the citation and number patterns here are ASCII-only).

## Places this plan cannot be verified until the owner runs it on the server

2. Flash-Lite's reply length, speed and reliability on the outcomes part.
3. Real token counts against 250,000 a minute when four parts follow the list call.
4. Whether real answers carry units and arms in the shape the chart rules expect (risk 3).
5. How the page looks on the owner's phone and in dark mode with real text lengths.

## Deferred to F4 (recorded after the fifth independent check, 12 Nov 2026)

The fifth check of the answer page found no wrong picture that a model answering from abstracts would plausibly produce, and no input that makes the page fail. These items are recorded for F4:

1. **Negated arm scored as the side it names.** "no TEP" or "non-Lichtenstein" scores as that procedure's side, because the side match ignores "no" and "non". The arm texts are shown as written. Fix in the scoring step, together with item 5.
2. **Time points or subgroups inside arm texts.** "TEP at 5 years" against "Lichtenstein at 1 year" get squares. The labels show the difference.
3. **Unit "HR" on something that is not a ratio** is drawn as a hazard ratio. Code cannot know; F4's number check must match unit and value to the abstract.
4. **Same label, different measures** in one study (any chronic pain and severe chronic pain) are drawn as one pair. Code cannot tell them apart.
5. **The squares rule is strict.** On made-up but realistic arm spellings, about 37% of genuine two-arm percent pairs get squares; the rest fall back to a named text row. Causes: singular against plural, abbreviations, comparisons shaped "X vs no X", and words shared with only one side. Options for F4: match singular to plural and treat "no"/"non" as removing the next word.
6. **A difference row does not say which arm minus which** (inherited from Incisive).
7. **In "Compare the arms" a value's confidence interval is checked but not printed.**
8. Cosmetic: "nonsignificantly" is not in the negation list; a unit of "MD" reads "2.1 MD" in the row's screen-reader text; "Absolute risk reduction" is listed with an unhelpful reason.

What code cannot remove: the model putting a wrong but well-formed label, unit or arm on a number. F4's number checks must match each drawn value, its unit and its arm against the cited abstract. Until then a drawn number is checked for shape, not for truth.
